## 2. 长期有效的项目判断

### 2.1 项目主目标

当前项目的真实目标是逐步形成一个“机会 / 竞赛信息平台”，而不是只维护单一竞赛页。

它当前包含四条能力线：

- 后端平台能力：用户、认证、机会、竞赛、画像、认定规则、爬虫任务
- 主业务前端：`unifocus/web/`
- 产品实验前端：`unifocus/web-vite/`
- 智能处理预留：`unifocus/nlp-service/`

### 2.2 当前阶段目标

当前阶段的优先级不是全栈闭环，而是：

1. 完善前端界面与页面覆盖
2. 维持主链路稳定可运行
3. 收敛主前端路线
4. 再逐步补齐登录、画像、简历、智能能力

### 2.3 当前已验证主链路

当前最可信的运行口径不是历史文档的理想态，而是已经验证过的链路：

- `postgres`：Docker
- `redis`：Docker
- `api`：Docker
- `web`：本地 Next.js
- `nlp-service`：当前阶段默认不作为阻塞项

## 3. 主线与实验线边界

### 3.1 业务主线

`unifocus/web/` 是当前真实业务主线。

当前已确认：

- `lint` 可通过
- `build` 可通过
- 已存在 `/ -> /dashboard` 重定向
- 已存在 `dashboard`、`dashboard/planet`、`dashboard/competitions` 三个真实页面入口
- `dashboard/competitions` 已接后端真实数据
- 竞赛页的 `useEffect` 依赖问题已修复
- `401 -> /login` 的错误跳转已清理
- 侧边栏未实现项保持禁用
- `planet` 的空数据崩溃已补兜底

### 3.2 实验线

`unifocus/web-vite/` 是当前产品表现与界面探索实验线。

当前已确认：

- 使用 `React + Vite + JavaScript + three.js`
- 已形成 “Dashboard / Planet” 双模式机会星球原型
- 当前更接近展示型产品前端与视觉参考，不应表述为已替代 `web/`

### 3.3 智能能力边界

`unifocus/nlp-service/` 当前只应被表述为“已存在部分实现的独立微服务”，不能表述成“已经完整接入主链路”。

当前真实状态：

- 入口存在
- 文本提取 / 向量化已有实现
- 不要求在当前前端完善阶段强制启动

## 4. 环境与配置特例

这些内容不是临时问题，而是应长期记住的开发约束：

- 当前机器上存在旧 PostgreSQL 监听 `127.0.0.1:5432`
- 这会影响“本地直接运行后端”时的数据库指向判断
- 当前 Docker 数据库角色历史上默认是 `unifocus`
- 为兼容本地开发配置，当前项目数据库中已补入 `yufan` 角色
- `yufan` 在本项目里不是单一语义：
  - 可能表示历史本机用户名
  - 可能表示数据库账号
  - 不等于网站业务登录用户
- 网站业务登录仍应按 `username / email / password` 体系理解

## 7. 审核与协作规则

### 7.1 审核优先级

评审变更时，优先检查：

1. 是否偏离当前阶段目标
2. 是否越过主线 / 实验线边界
3. 是否把实验能力误写成主线能力
4. 是否与当前已验证运行链路冲突
5. 最后才是代码风格与局部实现细节

### 7.2 协作方式

后续协作默认遵守：

- 先读文档，再动代码
- 先确认真实入口，再判断影响范围
- 重要改动后补一条“当前状态 + 边界 + 下一步”的文档更新
- 不把跨项目经验直接当当前项目事实使用

## 8. 跨项目迁移过来的管理经验

本项目已经确认可以长期借鉴这些做法：

- 固定“开工前必读顺序”
- 分开维护“项目现状”和“项目结构”
- 使用长期记忆文档沉淀决策、边界和环境特例
